01 · Guía de lectura

Propósito y alcance

Este manual explica cómo está construido el frontend del CRM Transitemos y cómo se comporta cada pantalla en el código actual. Está pensado para desarrollo, soporte, QA, auditoría técnica y transferencia de conocimiento.

Qué sí cubre

El frontend real

Rutas, guards, layouts, componentes, formularios, validaciones, estados, llamadas HTTP, permisos visibles, estilos, responsive y exportadores.

Qué no cubre

Lógica interna del backend

Se documentan contratos y roles observados, pero no se modifica ni se garantiza la implementación interna de FastAPI, SQLAlchemy o PostgreSQL.

Cómo se verificó

Lectura del worktree

Auditoría directa de frontend/src, configuración de Vite, pruebas existentes y endpoints del backend. Los diagramas se validaron con Archify 3.2.0.

La referencia es el worktree local en la rama main, con fecha de revisión 20 de octubre de 2026. Si cambia una ruta, un formulario o un endpoint, actualiza la sección correspondiente y vuelve a validar los diagramas.

02 · Lectura en dos minutos

Resumen ejecutivo

El CRM es una SPA React que centraliza la creación y el seguimiento de solicitudes internas, con un dashboard operativo, administración de catálogos y un módulo de reportes que exporta Excel y PDF sin intervención del backend.

11entradas de ruta en App.jsx (incluye raíz, alias y 404)
8páginas de aplicación + 404
3roles operativos: admin, técnico, solicitante
2formatos de exportación: XLSX y PDF

Fortalezas observadas

  • Separación clara entre páginas, layout, componentes reutilizables y utilidades de datos.
  • Rutas administrativas protegidas en el cliente y respaldadas por roles en el backend.
  • Un único modelo de reporte alimenta Excel y PDF, evitando cifras divergentes.
  • Compresión de datos y estados de carga/error visibles en las pantallas principales.
  • Diseño corporativo consistente y comportamiento responsive hasta móvil.

Puntos que requieren atención

  • Dashboard, listado y badge usan como máximo los primeros 100 tickets.
  • La gestión de tickets pagina en cliente sobre esos 100; no hay búsqueda en servidor.
  • Reportes carga hasta 10.000 tickets y no ofrece filtros de periodo o área.
  • El selector “Mantener sesión iniciada” no altera la persistencia del token.
  • La integración real no pudo validarse por conflictos de merge preexistentes en el backend.
!
No hay exportación CSV

El módulo de reportes expone únicamente Excel y PDF. El comentario antiguo que menciona CSV en reportData.js es residual; no existe botón, handler ni archivo reportExport.js en el flujo actual.

03 · Diseño general

Arquitectura del frontend

La aplicación se organiza en una capa de presentación (React + Vite), una capa de estado y acceso a datos (AuthContext, ToastContext y apiFetch), y una capa de salida (exportadores Excel/PDF). Todo el tráfico HTTP converge en la API FastAPI.

AR

Arquitectura por capas

Archify · validado
Lectura del diagrama: el usuario navega la SPA React; React Router resuelve rutas y guards; AppLayout compone sidebar y topbar; los módulos consumen estado y servicios; apiFetch adjunta JWT y llama a FastAPI; los exportadores generan XLSX/PDF en el navegador. La base de datos queda detrás de la API.
Fuente: docs/archify/arquitectura-frontend.architecture.json Abrir diagrama interactivo ↗
Capa 1

Presentación

App.jsx define rutas y carga diferida. AppLayout aporta sidebar, topbar, identidad y cierre de sesión. Cada página compone componentes de UI.

Capa 2

Estado y datos

AuthContext conserva usuario, token y rol. ToastContext muestra confirmaciones. apiFetch centraliza URL base, Bearer, JSON y refresh ante 401.

Capa 3

Salidas

reportData normaliza tickets y métricas; reportExcel construye tres hojas; reportPdf genera un informe carta horizontal con detalle paginado.

Flujo de una petición autenticada

  1. Un componente llama a apiFetch(path, options); nunca construye la URL del backend por su cuenta.
  2. apiFetch lee access_token de localStorage y añade Authorization: Bearer ….
  3. Si el backend responde 401 y existe refresh_token, intenta POST /auth/refresh una sola vez y repite la petición.
  4. Si el refresh falla, elimina ambos tokens y redirige a /login salvo que la petición sea de autenticación.
  5. El componente interpreta res.ok y muestra datos, ErrorBanner, EmptyState o un toast según el caso.

05 · Contrato de navegación

Catálogo de rutas

Rutas declaradas en frontend/src/App.jsx con BrowserRouter. La raíz redirige a /login; no existe redirección automática al dashboard para una sesión ya iniciada.

Orden de resolución

  1. ProtectedRoute comprueba solo que exista access_token en localStorage.
  2. AdminRoute espera a que AuthContext resuelva el rol con /me.
  3. Si el rol no es admin, redirige a /dashboard.
  4. Si no hay token ni usuario, redirige a /login.

Títulos y fallback

SECTION_TITLES mapea las rutas internas a títulos de topbar. Cualquier ruta desconocida dentro del layout mostraría “CRM Transitemos”, aunque el 404 actual queda fuera del layout.

El fallback de Suspense muestra “Cargando módulo…” con un spinner accesible.

06 · Identidad y control

Sesión, roles y permisos

El acceso combina una comprobación rápida de token en el cliente con la validación real del backend. El frontend decide qué mostrar; el backend decide qué permitir.

Estados de autenticación

  • Sin token: ProtectedRoute redirige a /login.
  • Token y rol cargando: AdminRoute muestra “Verificando permisos...”.
  • Token inválido: /me falla, se limpian los tokens y se vuelve al login.
  • Rol no admin: acceso administrativo redirige a /dashboard.

Roles y nombres

El rol efectivo se obtiene de user.role.name o, si el backend devuelve una cadena, de user.role. Los valores operativos son admin, tecnico y solicitante.

El backend valida con require_roles. Ocultar un botón no sustituye esa validación.

!
Riesgo de almacenamiento: los tokens viven en localStorage, accesibles para JavaScript. Es una decisión existente; cualquier cambio a cookies HttpOnly requiere coordinación con backend y no forma parte de esta documentación.
07 · Shell de la aplicación

Layout y navegación

AppLayout es el shell visual de todas las páginas internas. No se declara como layout de ruta: cada página lo importa y envuelve su contenido.

Sidebar

  • Marca, logo y subtítulo institucional.
  • Grupo Principal: Dashboard.
  • Grupo Solicitudes: Nueva solicitud y Gestión de solicitudes.
  • Grupo Administración, solo si role === 'admin': Reportes, Áreas, Usuarios y Roles.
  • Tarjeta de usuario con iniciales, nombre y rol; botón de cierre de sesión.
  • Badge de tickets abiertos en “Gestión de solicitudes”, calculado con los primeros 100 tickets.

Topbar

  • Botón de menú visible en mobile (< 960 px).
  • Título contextual desde SECTION_TITLES.
  • Nombre y rol del usuario; botón de logout con aria-label.
  • No incluye buscador global ni notificaciones.

Pantalla pública sin AppLayout. Usa un panel institucional a la izquierda y el formulario a la derecha; en móvil oculta el panel de marca.

Formulario

CampoTipoRegla / comportamiento
UsuariotextRequerido, autocompletado username; inicia con un valor de desarrollo precargado.

Acciones y estados

  1. El formulario llama a login(username, password).
  2. Si la API responde error, muestra el detail o un mensaje genérico en un banner rojo.
  3. Si es correcto, guarda tokens, actualiza el contexto y navega a /dashboard.
  4. El layout y AdminRoute pueden mostrar un estado breve de carga mientras /me resuelve el rol.

No hay recuperación de contraseña, registro público ni SSO en esta pantalla.

!
La raíz siempre lleva al login

/ redirige a /login incluso si existe un token. Un usuario autenticado que visite la raíz verá el formulario; no hay redirección automática al dashboard.

10 · Módulo

Nueva solicitud

Formulario de alta de tickets. Carga las áreas al montar, selecciona la primera por defecto y envía el conjunto completo a POST /tickets/.

Campos y validaciones

CampoControlValidación / comportamientoEnvío a la API
Título de la solicitudinput textRequerido; se convierte a mayúsculas al escribir; sin longitud máxima en cliente.title
Área responsableselectRequerido; deshabilitado mientras carga; opción “Sin áreas disponibles” si no hay catálogo.area (nombre)
Estado inicialinput deshabilitadoMuestra “Abierto”; no editable.status (el backend define el estado inicial)
PrioridadRadiosRequerida; por defecto Alta; cuatro opciones con descripción de impacto.priority
Descripción detalladatextareaRequerida; contador de caracteres; sin límite máximo en cliente; ayuda a no incluir datos sensibles.body

Flujo de envío

  1. Al montar, GET /areas/ llena el selector y asigna la primera área.
  2. El usuario completa título, prioridad y descripción.
  3. El submit se bloquea si ya está cargando o si las áreas aún no están disponibles.
  4. Se envía el objeto con title, body, priority, status y area.
  5. Si la respuesta es exitosa, toast “Solicitud creada correctamente” y navegación a /tickets.
  6. Si falla, se muestra el detail del backend o un mensaje genérico.

Observaciones

  • El backend declara TicketCreate con title, body, priority y area; el status enviado no forma parte del contrato y el servidor fija el estado inicial.
  • La ayuda de prioridad dice que el área podrá ajustarla, pero la interfaz de gestión no permite editar prioridad.
  • Si no hay áreas, no se puede crear un ticket; el formulario muestra un aviso informativo.
  • No hay adjuntos, comentarios, categorías ni solicitud de fecha de vencimiento.
11 · Módulo

Gestión de solicitudes

Pantalla operativa para consultar, filtrar y actualizar el estado de los tickets. Carga hasta 100 registros del backend, filtra y pagina en el navegador, y muestra el detalle en un modal.

Carga

100 tickets + áreas

GET /tickets/?limit=100 y GET /areas/. El backend filtra la visibilidad según el rol.

Interacción

Filtros y modal

Búsqueda por título/ID, filtros de estado, prioridad y área; paginación local de 10; detalle sin cambiar de ruta.

Permisos

Edición condicionada

Solo admin y técnico ven el selector de estado, el botón de cierre y el historial.

Filtros, búsqueda y paginación

ControlOpciones / alcanceComportamiento

SugerenciasPrimeras 6 coincidenciasAl hacer clic coloca el título completo en el buscador; no abre el detalle.
EstadoTodos, Abierto, En proceso, Resuelto, CerradoComparación exacta con el valor del ticket.

Indicadores del listado

KPICálculoAcción al hacer clicObservación
Totaltickets.lengthQuita el filtro de estado.Máximo 100 por la consulta.
AbiertasEstado normalizado abiertoFiltra por Abierto.—

Tabla y detalle

Columnas de la tabla

  • Ticket (#ID), solicitud (título + descripción truncada), área, prioridad, estado, fecha de creación y acciones.
  • La fila completa es clicable; el botón “Ver” y el selector de estado detienen la propagación.
  • El selector de estado aparece solo para admin/técnico y se deshabilita mientras actualiza ese ticket.
  • La fecha de la tabla usa es-CO con día, mes abreviado y año.

Contenido del modal

  • Estado, prioridad y área como badges; título en el subtítulo.
  • Área, creado, última actualización y “Actualizado por” con formato es-ES.
  • Descripción completa o texto de respaldo.
  • Historial de cambios para admin/técnico; para solicitante se explica que no está disponible.
  • Acciones: cambiar estado, “Cerrar ticket” si no está cerrado y “Volver al listado”.

Cambio de estado e historial

  1. El usuario elige un estado distinto en la tabla o en el modal.
  2. Aparece un window.confirm con el ID y el nuevo estado; si se cancela, no se envía nada.
  3. Se ejecuta PUT /tickets/{id} con { status } y se deshabilita el selector de ese ticket.
  4. Si responde bien, se actualiza el estado en la lista y en el ticket seleccionado; se muestra un toast.
  5. Si falla, se muestra un ErrorBanner, un toast de error y se fuerza el re-render para restaurar el valor controlado.
  6. “Cerrar ticket” reutiliza el mismo flujo con Cerrado y cierra el modal si la actualización fue exitosa.
!
La actualización local es parcial

Tras cambiar el estado, el frontend solo modifica status. No refresca updated_at, updated_by ni el historial dentro del modal. Para ver esos datos actualizados hay que recargar el listado o volver a abrir el detalle.

i
No hay transiciones restringidas en la UI

El selector permite pasar de cualquier estado a cualquier otro, incluido reabrir un ticket cerrado. La validación de negocio, si existe, queda del lado del backend.

12 · Módulo

Reportes y exportación

Módulo exclusivo de administración. Combina tres métricas del backend con el listado completo de tickets para mostrar KPIs y generar un libro Excel o un PDF institucional.

RP

Flujo de datos y exportación

15 · Contrato observado

Integración con la API

Todas las llamadas de la aplicación pasan por apiFetch, salvo el refresh interno y la carga del logo para el PDF. La URL base se toma de VITE_API_URL o del valor local http://127.0.0.1:8000.

SQ

Secuencia de una petición con JWT y refresh

Archify · validado
Lectura del diagrama: el componente solicita datos, apiFetch adjunta el Bearer, la API responde 200 o 401; ante 401 se intenta /auth/refresh una vez, se guardan los nuevos tokens y se repite la petición. Si el refresh falla, se limpia la sesión y se redirige al login.
Fuente: docs/archify/secuencia-api.sequence.json Abrir diagrama interactivo ↗

Configuración de red

URL y CORS

  • Por defecto, el frontend llama directamente a http://127.0.0.1:8000.
  • El proxy de Vite (/auth, /tickets, /areas, /metrics) solo se usa si VITE_API_URL es una ruta relativa.
  • El backend permite CORS desde http://localhost:5173 y http://127.0.0.1:5173 por defecto, configurable con CORS_ORIGINS.

Cabeceras y cuerpo

  • Accept: application/json siempre.
  • Content-Type: application/json solo si hay body.
  • Authorization: Bearer <access_token> si existe token.
  • El cuerpo se serializa con JSON.stringify; no se envían FormData ni archivos.

Flujo administrativo

  1. El admin entra a Áreas, Usuarios o Roles desde el menú.
  2. Crea el registro; el frontend aplica trim/mayúsculas cuando corresponde.
  3. El backend valida duplicados, existencia y asociaciones.
  4. La UI recarga la lista y muestra un toast o un error.

  2. Se eliminan tokens y se limpia el contexto.
  3. Se navega a /login.
  4. Las rutas protegidas vuelven a exigir token.

Qué funciona bien

  • La sidebar móvil bloquea el scroll y se cierra con Escape o overlay.
  • Las tablas conservan legibilidad mediante scroll horizontal contenido.
  • Los KPIs y gráficas se apilan sin romper el layout.
  • El modal limita su altura al viewport y reduce márgenes en móvil.

Qué revisar en dispositivos

  • Tablas con muchas columnas siguen dependiendo de scroll horizontal.
  • El menú móvil no atrapa el foco; el foco puede escapar al contenido de fondo.
  • Los textos largos de títulos/áreas pueden truncarse; conviene probar con datos reales.
  • El PDF no está pensado para pantallas pequeñas; es una descarga, no una vista.

Guía de mantenimiento

Puntos de entrada y convenciones para cambiar el frontend sin romper navegación, permisos o exportaciones.

Comandos del proyecto

frontend · PowerShell / terminal
cd frontend
npm install
npm run dev       # Vite en desarrollo
npm run lint      # oxlint
npm test          # Vitest run
npm run build     # build de producción
npm run preview   # servir el build

Agregar una ruta o pantalla

  1. Crear la página en frontend/src/pages y envolver el contenido en <AppLayout> si es interna.
  2. Importarla con lazy() en App.jsx y declararla dentro de ProtectedRoute o AdminRoute.
  3. Agregar el ítem al grupo correcto de navGroups en AppLayout.jsx.
  4. Registrar el título en SECTION_TITLES.
  5. Documentar la ruta en este manual y ejecutar lint, tests y build.
App.jsx · patrón de ruta protegida
<Route element={<ProtectedRoute />}>
  <Route path="/dashboard" element={<DashboardPage />} />
  <Route path="/tickets" element={<EstadoTicketsPage />} />
</Route>

<Route element={<AdminRoute />}>
  <Route path="/reportes" element={<ReportesPage />} />
</Route>

Agregar una llamada a la API

Patrón recomendado
import { apiFetch } from '../apiClient';

const res = await apiFetch('/recurso/?limit=100');
if (!res.ok) throw new Error('No se pudo cargar el recurso.');
const data = await res.json();

No construir URLs absolutas ni leer tokens manualmente. El refresh, el Bearer y la redirección por 401 ya están centralizados.

Regenerar los diagramas Archify

i
Archify 3.2.0 no es una dependencia de ejecución

El paquete archify@0.0.4 de frontend/package.json es una utilidad legada de árbol y no se importa en la aplicación. Los diagramas de este manual se generaron con el CLI/skill Archify 3.2.0, fuera del bundle. No agregues imports de Archify al frontend.

Flujo de documentación
archify validate architecture docs/archify/arquitectura-frontend.architecture.json
archify validate workflow docs/archify/navegacion.workflow.json
archify validate workflow docs/archify/flujo-reportes.workflow.json
archify validate sequence docs/archify/secuencia-api.sequence.json

archify finalize architecture docs/archify/arquitectura-frontend.architecture.json \
  docs/archify/arquitectura-frontend.html --out-dir docs/archify

Los cuatro artefactos actuales pasaron validate, deliver, check y browser-check. Si cambia el código, actualiza el JSON, vuelve a finalizar y revisa el HTML en el navegador.

Buenas prácticas observadas

  • Mantener un único modelo de reporte para Excel y PDF.
  • Reutilizar apiFetch, Feedback y los tokens de ui.css.
  • Validar siempre res.ok y ofrecer un estado de error comprensible.
  • Probar los límites de paginación con más de 100 registros.
  • Verificar el comportamiento en 960, 700 y 480 px.
  • No asumir que el frontend es la única barrera de permisos.
  • No duplicar colores de estado en CSS o PDF.
  • No agregar endpoints de exportación sin coordinar backend.
  • No documentar CSV como si existiera: hoy no está implementado.
  • No commitear la documentación sin solicitud explícita.

Checklist de aceptación

Documentación

  • Rutas, guards y títulos revisados contra App.jsx.
  • Formularios y acciones revisados contra cada página.
  • Endpoints, roles y límites contrastados con el backend observado.
  • Exportadores Excel/PDF documentados sin afirmar CSV.
  • Limitaciones y deuda técnica registradas.

Entrega

  • Manual autocontenido, sin dependencias de red.
  • Búsqueda, navegación, copiado e impresión incluidos.
  • Diagramas Archify embebidos y enlazados.
  • Sin credenciales, tokens ni datos personales.
  • Sin cambios funcionales ni commit no solicitado.
